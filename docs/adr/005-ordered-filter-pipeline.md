# ADR-005：采用有序短路过滤流水线

- 状态：Proposed
- 日期：2026-09-26
- 相关提交：[`616b9e2`](https://github.com/svlic/TFor/commit/616b9e2dcbd634a50640d576440d63ec80fffb56)、[`cd59c27`](https://github.com/svlic/TFor/commit/cd59c270eb34c6b801aa1f126978646dc5912d61)

## 背景

规则需要按消息正文和发送者信息筛选消息，但当前不希望引入更复杂的通用规则引擎。

## 决策

每条规则包含按位置执行的过滤步骤。步骤支持：

- blacklist 或 whitelist；
- 正文、发送者名称、username 或 sender ID；
- contains、exact 或 regex；
- 一个步骤内多个值采用 ANY 语义。

blacklist 命中或 whitelist 未命中时立即拒绝并停止后续步骤。sender ID 转换为字符串后允许使用上述三种匹配方式，以支持按发送人过滤。

正则表达式必须在保存规则时校验；非法表达式应拒绝保存，而不是进入运行时后静默视为不匹配。

## 可确认的实现事实

- `filter_steps` 按 `position,id` 排序。
- Web 保存流程会校验步骤枚举值并编译每个 regex，非法配置会拒绝保存。运行时仍保留非法 regex 不崩溃的防御行为，用于兼容旧数据或直接数据库修改。
- 日志只记录步骤、匹配方式及 PASS/REJECT，不记录过滤值或命中片段。

## 后果

- 执行语义简单、可预测，并可输出逐步骤结果。
- 当前只有隐式 AND 与短路，不支持嵌套布尔表达式。
- 保存时校验可以避免配置错误被静默忽略。

## 未决问题

- 过滤步骤复用、嵌套或增强可解释性存在需求，但具体使用场景和优先级尚未明确；在明确前不扩展为复杂规则引擎。
