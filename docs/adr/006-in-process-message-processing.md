# ADR-006：使用进程内异步任务处理消息

- 状态：Proposed
- 日期：2026-09-26
- 相关提交：[`616b9e2`](https://github.com/svlic/TFor/commit/616b9e2dcbd634a50640d576440d63ec80fffb56)、[`cd59c27`](https://github.com/svlic/TFor/commit/cd59c270eb34c6b801aa1f126978646dc5912d61)

## 背景

系统需要同时处理多个账号和规则，不严格要求源消息顺序。目标是尽量不漏发；故障场景允许重复发送。

## 决策

使用 asyncio 进程内任务执行规则。每条匹配规则独立处理，不提供严格顺序保证。延迟计时不占用全局规则执行槽；延迟完成后重新读取规则和源消息，源消息已删除时不发送。

相册按 `grouped_id` 聚合并整体重取、过滤和发送。同一来源事件的即时规则共享事件消息或一次相册重取；延迟和 FloodWait 重放规则分别重新读取。当前接受进程重启导致尚未执行的普通延迟任务丢失，不为所有延迟任务建立持久队列。

规则处理采用全局并发上限，默认同时执行 10 条规则，可通过 `TFOR_MAX_CONCURRENT_RULES` 调整。普通规则任务另有默认 1000 的内存上限，达到后消息入口等待可用容量，而不是继续无界创建 task。

## 可确认的实现事实

- 每条普通规则在取得待处理容量后通过 `asyncio.create_task` 启动，并在实际执行前获取全局 semaphore。
- 相册首次事件等待 1 秒，然后在触发消息附近最多扫描 60 条消息。
- 待处理相册、任务和已发送消息集合都只存在内存中。
- 普通延迟任务仍只在内存中；超过配置阈值的 FloodWait 会写入 SQLite `deferred_jobs`，由单个后台 worker 分批恢复。
- Telethon 的自动 FloodWait 休眠被关闭，RPC 服务端错误重试显式收敛为 3 次；应用不再重复重试 `ServerError`，只处理 FloodWait 和网络层临时错误，避免内外层重试叠加。
- 当前没有持久幂等键，故障恢复仍可能重复发送。

## 后果

- 实现轻量，正常运行时规则之间互不阻塞。
- semaphore 限制实际执行并发，待处理容量限制等待与执行中的普通规则任务；入口达到上限时会产生处理延迟。
- 进程故障可能漏发，发送成功但状态未记录等故障可能导致重复；重复发送符合允许的退化语义。
- 固定相册等待和扫描窗口未经真实流量依据验证。

## 未决问题

- 是否需要对任务积压实施背压或丢弃策略？
- 是否需要从全局上限进一步演进为每账号或每目标上限？
